# 首版实现决定与开发问答

版本：v0.2；日期：2026-11-14；适用阶段：Research Agent 主线 M1—M3。

后续评测调整：本文保存首版实施约定。主线现按[单任务评测方案](feedback-comparison-plan-v1.md)验证研究过程中利用反馈的效果，跨任务经验对照作为扩展；本文的 1.10× 达标即停、300 秒 / 6 请求 / 4 候选仍是已实现的短运行默认值，新长时协议尚待实现。模型服务等实际运行配置见各批次报告，不以首版决策替代。

本文整理并确认了首版实施中的 14 项核心设计与工程边界决策，将[核心 PRD](../requirements/core-requirements.md)落实到首版样例、模型、数据、运行环境和交付标准。团队已选择 [Research Agent 赛道](../requirements/product-requirements.md)，企业方补充原文与团队确认见[补充说明](../requirements/competition-brief.md)。

团队已确认：小模型使用自部署 Qwen，大模型使用 OpenAI GPT-6.1 Sol，推理强度 `xhigh`；暂不设置金额上限；模型凭据通过本地环境配置注入。开发和正式演示固定在同一台机器、同一 Docker 环境。其余实现细节按下面的首版约定推进。

## 1. 主指标与初始程序

问题摘要：样例是修复错误，还是在正确性约束下优化性能；主指标和计时方法是什么？

初始程序正确，优化目标是性能。输出必须保证结果正确；主指标为候选程序的处理耗时，加速比定义为 `初始程序耗时中位数 / 候选程序耗时中位数`。首版任务目标设为加速比至少 1.10，作为停止和任务成功判定阈值。

初始版本使用直观的标准库实现。若首轮未测出足够优化空间，应检查任务设计与输入规模，而不以降低基线质量的方式调整基准。

迭代停止依据开发验证指标，最终任务达标以独立最终测试的正确性与加速比为准。输入规模和测量配置先在 A 上校准，再冻结到完整对照；小输入测不出可靠差异时如实保留原结果。

候选出错时需要修复，指优化过程中产生的错误；不再单独开发缺陷修复任务族。初始程序也是一个经过验证的候选，后续全部失败时保留它，报告“无改进”或实际终止原因。

时间分开统计：程序处理耗时衡量产物性能；整个 Agent Run 的实际耗时、模型等待、工具耗时和 Token 衡量系统效率。

## 2. 任务定义、数量与重复次数

问题摘要：一个任务是同一程序配不同输入，还是不同程序；每批多少任务，每种配置重复运行几次？

首版只做一个任务族：按 key 对记录分组，计算每组的数量与整数求和，按 key 升序输出。输入字段为字符串 `key` 和有符号整数 `value`；空输入输出空列表。整数求和与排序语义固定，避免浮点误差和无关的格式清洗问题。

一个 Task 是一份冻结的任务包：语义契约、初始代码、开发数据、独立最终测试数据、生成器版本与种子、评价规则、运行限制。M1 各实例复用同一份初始代码，通过数据规模、key 基数、重复程度、分布偏斜和有序程度形成不同输入条件。此阶段的效果结论限定为同一任务族内的迁移。

| 用途 | 首版规模 | 执行约定 |
| --- | --- | --- |
| M1 连通与功能检查 | A 中 1 个实例 | 跑通正确候选、错误候选、预算停止；失败机制可用固定测试候选检查 |
| A 学习与开发 | 6 个实例 | 学习模式串行运行，最终冻结一个学习后的快照 |
| B 开发对照 | 6 个实例 | 每个实例、每种冻结配置各运行完整 Agent 3 次 |
| C 最终留出 | 6 个实例 | 配置冻结后执行一轮预先确定评测，每个实例、每种配置各运行 3 次 |
| 现场演示 | 从已冻结清单选择 1—2 个实例 | 依据实测耗时安排；现场观测与完整评测报告分别标注 |

B/C 各包含同类新实例与条件变化的实例，例如小输入、key 种类多、乱序输入，使 A 中观察到的优化不必处处成立。数据清单在查看效果前冻结，不能先跑一批再挑有收益的任务纳入报告。

两种重复不能混为一谈：

- **程序测量：**基线与候选各预热一次，再交替进行 5 次正式测量，保存原始值、中位数与离散程度。每个样本使用干净进程和新的输入对象，禁止沿用候选输出缓存。计时由容器外评测器掌握，从发送输入到收到完整输出；容器启动和镜像准备单列，不计入程序处理耗时。
- **Agent 重复：**每次从相同初始代码、指定冻结快照和空任务状态开始，重新让模型决策与生成候选。每个任务报告全部 3 次结果、达标次数及耗时/费用分布，不只选最好一次。旧新配置交替运行，不并发争抢测量资源。

这 3 次重复观察固定快照下的运行波动；模型不支持固定 seed 时在配置中注明。

## 3. Agent 可见内容与验证边界

问题摘要：Agent 能看到哪些样本、输入和参考输出；如何防止方案过拟合测试样例？

Agent 可以看到任务语义、初始代码、少量可见输入输出样例、开发数据的概况，以及开发验证的反馈。开发验证可以返回错误类别和少量可公开的反例，帮助修正候选。

最终测试的输入、参考输出和测试生成种子不提供给模型，也不进入经验检索。最终候选冻结后再测试；结果可进入最终报告，不反馈给该 Run 继续选方案。冻结候选在最终测试失败时按实际结果记为未通过。

候选运行时必然需要处理本次输入，但容器只接收该次输入和候选代码，不挂载参考输出、完整测试库或评测器。参考输出的计算与比较在候选容器外由裁判完成，均以隔离沙箱测得结果为准。

## 4. 模型、接口与预算

问题摘要：使用哪家模型和接口，调用预算是多少，费用按哪个版本的价表记录？

| 角色 | 首版配置 | 接入与记录 |
| --- | --- | --- |
| 常规执行 | 团队自部署 Qwen | 使用现有服务的实际接口；由部署方补充准确 model ID、版本/量化配置、服务地址及用量返回方式 |
| 升级诊断与候选生成 | OpenAI `gpt-6.1-sol` | 使用 Responses API，`reasoning.effort = "xhigh"`；保存请求配置、返回模型标识和用量 |

GPT-6.1 Sol 官方文档确认支持 `xhigh`，其工具调用要求使用 Responses API。Qwen 是否兼容 Chat Completions 取决于现有部署，不能因接口外形类似就假定两条路径都支持同一种协议。[模型与接口依据](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

首版使用简单、固定的升级规则：先用 Qwen；连续两次候选尝试未获得正确且达标的结果，并且还有运行额度时，升级到 GPT。升级后本 Run 保持使用 GPT，不来回切换。每次记录触发条件与依据；API/网络错误单独记录，不自动归因于模型能力。模型仍负责选择具体实验和修正方法。

首版不引入专用决策模型或学习路由权重。旧新经验对照固定两条模型配置、`xhigh` 和升级规则；经验可能让 Qwen 更早得到有效候选，从而减少升级。若要修改路由规则，单独记录配置版本并重做对照。

费用暂不设硬上限；默认每 Run 最多 6 次模型请求、4 个候选，实际耗时上限 300 秒，单次模型请求上限 120 秒，单个程序测量上限 10 秒。输出长度设置显式上限并写入配置。以上是开发接口联测的运行边界，真实测量后可在 A 上调整，进入 B/C 对照前冻结。到达边界后保存已有产物和账本，不再额外调用模型总结。

`xhigh` 按用户选择保留。Research Agent 的现场节奏依据实测耗时安排；旧新经验对照保持相同推理强度。[推理强度与延迟依据](https://developers.openai.com/api/docs/guides/reasoning)

费用保存所用价表、日期、币种、计价单位和服务档位。直连官方 Standard 且输入不超过 272K token 时，可先以 2026-11-13 官方模型页价格估算：每百万未缓存输入 / 缓存输入 / 输出分别为 2 / 0.10 / 10 美元，缓存写入另按对应计价项处理。服务方实际账单优先；其他通道使用其实际价表。Qwen 的 API 支出与自部署机器成本分列，未核算的机器成本标记未知。[价格依据](https://developers.openai.com/api/docs/models/gpt-6.1-sol)

## 5. 技术栈与仓库结构

问题摘要：是否采用 Python 3.12、SQLite 和自写最小循环；后端目录之外是否需要单独的前端仓库？

后端采用 Python 3.12、SQLite、FastAPI，自行实现最小执行循环。候选程序仅使用 Python 标准库。项目按一个仓库协作，后端放 `backend/`，前端放 `frontend/`，文档放 `docs/`，无需另建前端仓库。

M1 先提供命令行复现入口与后端接口；不引入 LangGraph，也不开发通用模型网关或任务插件体系。两条实际模型接口只做完成当前动作协议所需的适配。

## 6. 候选执行与测量环境

问题摘要：候选代码在 Docker 还是受限子进程运行；开发与现场是否使用同一台机器？

使用 Docker，开发和现场固定同一台机器、同一镜像与资源配置。登记 CPU 架构、Python 版本、镜像摘要、Docker CPU/内存额度及模型服务版本。macOS 的 Docker 虚拟化和宿主机负载仍会影响计时，重复测量与串行对照继续保留。

候选容器禁网、非 root、只读根文件系统，使用临时工作目录，并限制 CPU、内存、进程数、执行时间和输出大小。候选代码不能访问模型凭据、Docker socket、经验数据库和评测答案。启动容器的权限由后端持有，模型只能调用受限的候选评测工具。

机器、镜像、资源限制变化后重新测基线及两种配置，不能把换机前后的耗时拼成对照。

## 7. 经验由谁生成

问题摘要：经验由 LLM 总结还是由程序生成；如何计入总结成本，并在预算耗尽后停止额外调用？

首版由程序从结构化执行记录提取经验事实，不增加单独的 LLM 总结调用。至少保存任务概况、动作/候选引用与代码哈希、验证结果、性能值、资源消耗及来源步骤。

检索注入时提供相关的候选修改片段及其验证事实，不能只给模型一个文件路径或哈希；片段与使用条件均可回溯到原始候选。

模型在行动时可以提交方案说明、预期和假设，这部分成本计入当前请求；模型解释与程序实测事实分开存储；程序仅记录“在特定观测条件下取得了何种实测结果”。

## 8. 成功 失败与无收益经验

问题摘要：什么记录有资格进入经验库；失败尝试是否也作为经验，并在后续检索时提供？

三类都保存：正确且有收益、正确但无收益、验证失败。经验必须有对应候选、评测结果和来源步骤；缺少结果的想法只保留为假设。

API 失败、环境错误、超时和错误输出分别标识。网络超时不记作“这个算法错误”，进程超时也不等价于已证明复杂度过高。

检索时在相关记录存在的前提下同时提供成功与失败经验，并显示样本数。写入的事实来自学习任务允许使用的开发验证；独立最终测试结果只用于报告，不流回当前学习快照。隐藏输入与答案不因写经验而变成模型可见内容。

## 9. 版本、回退与并发

问题摘要：版本能否分叉；回退后学习如何生成新版本；学习是否并发，是否需要快照合并？

首版学习模式全局串行，每个 Run 开始时固定读取一个快照。合格记录在结束时原子发布为新快照；没有合格新增记录时不制造空版本。

快照不可变，保存 `parent_snapshot_id`；当前生效版本用独立指针表示。版本编号全局递增。回退到 v2 后再次学习可以得到 v4，其父版本是 v2；v3 仍保留，不合并进 v4。首版不做分支合并或专门的分支管理界面。

运行中的 Run 不随回退切换快照；学习 Run 执行期间，界面不接受改动生效指针，避免结束发布时覆盖回退操作。A 批串行学习可产生多个版本，对照使用最终冻结的快照，并保存每个版本的来源研究 Run。

## 10. 检索特征来源

问题摘要：检索所用任务特征由人工标注，还是由数据概况工具计算？

人工登记任务类型、语义约束和允许工具。可计算的输入特征由程序对开发数据生成：记录数、key 基数、重复率、最大 key 占比、有序程度，并保存概况版本。

首版数据量允许时计算精确统计；若改成抽样，记录样本量与 seed。检索不读取最终测试概况，固定筛选规则和阈值，不额外调用模型判断经验相关性。

## 11. 模型字段与路由范围

问题摘要：原先以单 LLM 起步时，是否应为多模型路由保留每步所用模型和升级次数等字段？

当前已确定两条模型路径，因此每次模型调用必须记录 provider、实际 model ID、角色、推理配置、输入/输出用量、耗时、价格版本及请求标识。来源信息随 Step 进入 Experience。

升级次数从实际 Qwen 到 GPT 的转换计算，未尝试路径保持未知。首版只实现这两个已确定的接入，不设计任意模型注册、模型市场或复杂路由训练。

## 12. 界面与实时进度

问题摘要：使用网页、Streamlit 还是命令行加静态报告；是否需要实时显示步骤？

采用 FastAPI 加简单网页。页面包含运行步骤、预算与用量、最佳候选、经验证据、版本回退和旧新对照；前端沿用团队熟悉的 React 方案即可。

需要实时看到步骤级进度：模型开始/结束、候选评测、指标、升级原因和终止状态。首版通过轮询运行事件实现，不要求 token 逐字流式显示。JSON 运行报告与命令行复现入口同步提供，供脱离页面验收。

## 14. A、B、C 划分与最终验收

问题摘要：是否预先准备 A/B/C 三批，避免在 B 上调参后临时再造最终测试；C 只用一次如何理解？

一开始准备 A/B/C，各 6 个任务包，输入与 seed 独立；每个包内部另有开发数据与最终测试数据。A 用于学习和开发，B 用于开发期对照与调试，C 封存到配置冻结后的最终验收。

B 使用冻结经验且不写入持久经验库；团队根据 B 调整了提示词、检索、路由或其他配置后，B 就是开发证据，最终收益以 C 为准。C 的“一次”指一轮预先登记的验收，包含第 2 节规定的重复次数，不是只调用模型一次。

C 的完整清单、对照配置和重复次数在开跑前冻结。结果不用于继续调优；若继续依据 C 修改方案，它就失去独立留出资格，需另备新测试数据。最终报告保留失败与无收益实例。

## M1 开工与交付检查

现在可开始任务定义、Docker 执行器、外部评测器、账本和最小循环。模型准确部署标识、服务端点与凭据通过环境配置单独接通，不阻塞核心模块实现。

M1 交付应证明：基线正确且可重复计时；候选答案由外部裁判验证；错误候选不覆盖最佳产物；两个模型都能完成实际调用并记录升级；请求失败和运行上限可准确终止；从入口命令能复现结果。固定候选只用于功能检查，正式效果记录必须来自真实模型运行。
