# RouteEvo 现场演示脚本（Research Agent）

目标时长 6—8 分钟。顺序按 PRD 第 11 节：研究问题、预算和基线 → 一条真实的证据—假设—实验—修正链 → 最佳方案、独立结果和资源账本 → 系统本身的评估。所有数字都来自真实运行记录；现场新跑的运行和事先完成的评测分开说明，不把历史实验说成现场执行。

## 0. 开场前（提前 15 分钟）

```sh
open -a OrbStack                                 # Docker
ollama ps                                        # 确认 qwen3.8:27b-mlx 已加载；没有就先跑一次 probe 预热
cd backend
uv run routeevo probe small                      # Qwen 预热，期望 10—20 s 内返回 propose_candidate
uv run routeevo probe large                      # GPT 连通性，约 20 s、约 $0.01
uv run routeevo snapshots list                   # 确认生效版本是第二版学习的最终快照（* 标记，见 docs/results.md 2.1）
uv run routeevo serve                            # 浏览器打开 http://127.0.0.1:8000
```

- 浏览器全屏，缩放 110%—125%，投影上数字要清楚。
- 确认没有运行在执行（左下角显示“空闲”）。

## 1. 研究问题、预算和基线（1 分钟）

打开「01 研究运行」，选 A-01 的第一版学习运行（`#run/run-20261113T161733-7c5a`），展开“研究任务 · 运行开始前固定”：

- 研究问题：在输出完全正确的前提下，能否让这段分组聚合程序在该工作负载上至少快 1.10×？
- 基线：初始程序（csv + 两个 dict + sorted），开发数据中位耗时 0.679 s。
- 允许修改、工具、验证方法、预算（6 次请求、4 个候选、300 秒）都在开始前固定，模型改不了；最终测试数据不可见。

## 2. 一条真实的研究链（1.5 分钟）——“反馈改变了下一步”

同一页往下看“假设与实验”和“决策账本”：

1. Qwen 的假设：按字节解析、bytes 作 key 能省掉 str 转换，预期 ≥ 1.10×。实测 **0.90×，判定被反驳**。
2. Qwen 据此修正：“c1 慢是因为 bytes key”，改用 str key——但输出格式错误，**未能检验**。
3. 连续两次未达标，程序按固定规则**升级到 GPT**（账本写明触发条件）。
4. GPT 读到具体反馈，提出批量分行 + 单字典：**1.45×，得到支持**，达标后停止。
5. 判定由程序根据评测给出，不是模型自评；失败和被反驳的实验都留在记录里。

## 3. 对系统本身做研究（1.5 分钟）——第一版的发现与第二版的修改

打开「00 总览」，先看最下方的 C 批（第一版，只有文字经验）：

- 有经验后请求 3 → 1、费用下降、达标率不变，但**最终加速比中位数 1.41× → 1.29×**。
- 诊断：经验里已经有完整的好程序，Qwen 却要花一次请求把它重抄一遍（A-04 的“新”候选与 A-01 的 GPT 程序逐字相同）；而且一达标就停，用不上 GPT 找到的更快方案。
- 修改：经验保存完整程序；新任务首次请求前，由程序复验条件最接近的 ≤ 3 个已验证程序。评测运行复验达标即交付；学习运行把目标提高到超过已知最佳 5%，模型只做“超越”。
- 公平性：修改后重新学习、重新对照；C 已经用来诊断，所以在写第二版代码之前新封存了 D 批（提交 `d542906`），只跑一次。

## 4. 第二版的学习与验收（2 分钟）

1. 「01 研究运行」打开一次第二版学习运行（推荐 A-06 第 1 轮）：前三步是“程序 · 复用已验证程序”，没有模型参与；随后“提高本次目标”，模型以最佳复用程序为父候选提出超越方案，判定按当时目标给出。
2. 「00 总览」看学习阶段：A 批两轮，各任务最终加速比逐轮提高（数字见 `docs/results.md` 2.1）。
3. 看 D 批（封存留出）与 B 批（开发对照）的条带：达标率、最终加速比中位数、模型请求、GPT 费用、循环时长。进入「03 对照结果」看逐任务点图。
4. 如实讲代价与反例：学习阶段本身花钱更多（学习运行用 GPT 去超越已知最佳），学习成本单列；经验覆盖不到的工作负载（高基数），复验不达标，照常交给模型研究。

## 5. 现场新跑一次（约 1 分钟）

「01 研究运行」→ 新建运行：任务选 D-01（或任一 B 任务），模式“评测”，快照选第二版最终快照，点击开始。

预期：程序依次复验 3 个已验证程序（每个约 8—10 s），达标后直接冻结最佳程序做最终测试，**模型请求 0、费用 $0**。这是现场执行，与第 4 节的历史对照分开说明；单次结果只说明流程，效果以对照为准。

如果复验没有达标（例如选了高基数任务），运行会继续交给 Qwen/GPT，账本如实记录。

## 6. 交付与回退（30 秒）

- 运行页“导出研究记录（Markdown）”；完整交付包见 `docs/research/`：研究记录、`best.py`、全部候选、原始模型调用、`reproduce.sh`。
- 「04 版本管理」：选 v0，填写原因，设为生效版本，指针历史新增一行；之后的运行读取 v0，历史全部保留。演示后切回第二版最终快照。

## 7. 常见问题

| 问题 | 回答要点 |
| --- | --- |
| 复用旧程序算不算“作弊”或缓存？ | 复用的是经验快照里版本化、可回退、可追溯来源的已验证程序；每次都在新任务的数据上重新评测，未达标就不用。v0 没有程序可复用，两边配置相同，只换快照。 |
| 这是研究还是在轮流试预设选项？ | 没有预设候选清单。复用的程序来自以前的实验；模型候选由模型根据实测反馈写出，账本里能看到“c1 慢是因为……”这类直接引用反馈的修正，学习运行还要超越已知最佳。 |
| 经验是模型自己总结的吗？ | 不是。程序从结构化执行记录中提取事实和程序；模型的解释另存为未验证假设，不额外调用模型做总结。 |
| 怎么防止模型作弊？ | 候选在禁网、只读的容器里运行，只拿到 stdin；参考输出和最终测试数据不进容器；7 个契约用例防止只对当前数据分布正确的程序。 |
| 加速是不是噪声？ | 交替测量 5 轮，只有全部候选样本快于全部基线样本才算改善；同一个程序测出 1.05× 也不会被记成改善。 |
| B、C、D 有什么区别？ | B 是开发对照，可以据此调整；C 是第一版配置冻结后的留出，结果用于诊断；D 在第二版实现前封存，第二版定型后只跑一次。 |
| 费用怎么算？ | 每次调用记录服务方返回的用量，按带版本的官方价表估算；没有用量就记“未知”，不写 0；本地 Qwen 无 API 费用，机器成本单列为未核算。 |
