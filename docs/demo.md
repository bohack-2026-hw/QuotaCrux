# RouteEvo 现场演示脚本

目标时长 6—8 分钟。所有展示内容都来自真实运行记录；现场新跑的运行与事先完成的完整评测分开说明。

## 0. 开场前（提前 15 分钟）

```sh
open -a OrbStack                                 # Docker
ollama ps                                        # 确认 qwen3.8:27b-mlx 已加载；没有就先跑一次 probe 预热
cd backend
uv run routeevo probe small                      # Qwen 预热，期望 10—20 s 内返回 propose_candidate
uv run routeevo probe large                      # GPT 连通性，约 20 s、约 $0.01
uv run routeevo snapshots list                   # 确认生效版本是学习得到的最终快照（* 标记）
uv run routeevo serve                            # 浏览器打开 http://127.0.0.1:8000
```

- 浏览器全屏，缩放 110%—125%，投影上数字要清楚。
- 确认没有运行在执行（左下角显示“空闲”）。正式 B/C 对照期间不要现场运行，以免干扰计时。

## 1. 总览（1 分钟）——“只换经验，结果是否更好”

打开「00 总览」：

1. 一句话定位：模型、提示词、预算、评测器全部固定，只有经验快照在变化。
2. 左上：A 批 6 个任务串行学习，v0 → 最终快照；指出有两个高基数任务即使升级到 GPT 也没有改进，失败和无收益也被记录成经验。
3. 右上：三行进化说明，逐行读——比什么、学到什么、如何回退。每个数字都能点进对照页核对。
4. 下方：B（开发对照）与 C（最终留出）的达标率、请求数、升级次数、费用、耗时，旧/新两版并列。

## 2. 现场运行一次（2 分钟）——“每一步都有目的、预期和实际反馈”

进入「01 任务运行」，选择一个 B 任务（推荐 B 批中 Qwen 通常一两次请求就能完成的任务，见 `docs/results.md` 的请求列），模式“评测”，快照“当前生效版本”，点击开始运行。

边跑边讲：

- 顶部四个状态分开显示：候选运行完成、开发验证通过、指标改善、最终测试达标——“跑完”不等于“成功”。
- 预算仪表：请求、候选、循环时长。
- 右侧“本次实际读取的经验”：读了哪几条、匹配几个特征、来自哪个 A 任务。
- 决策账本：模型写下目的、预期和标为“未验证”的假设；程序给出评测反馈和下一步。
- 候选加速比条：朱红竖线是 1.10 目标，只有全部样本快于基线才计改善。
- 结束后点“导出研究记录（Markdown）”。

如果现场模型请求失败或超时：账本会如实显示“接口错误/超时”和终止原因。这本身就是 AC-08 的演示，然后切到运行记录里事先完成的同任务运行继续讲。

## 3. 经验（1 分钟）——“经验不是聊天记录”

在运行页点击某条读取的经验，跳到「02 经验查看」：

- 卡片第一句话：在什么条件下、做了什么、实测多少；左侧色条表示成功、无收益或失败。
- “模型解释 · 未验证”和测得事实分开；来源可以点回原始运行的那一步。
- 展开 diff：相对初始程序到底改了什么。
- 筛选“失败”：例如格式错误、契约用例失败，这些同样会在后续任务里告诉模型哪里会出错。

## 4. 对照（1 分钟）——“在没见过的任务上比较”

「03 对照结果」选 C（或 B）：

- 配置指纹一致；36 次运行全部列出，包括失败。
- 点图：每个任务一行，蓝色是 v0，橙色是新经验，实心表示达标，空心或“未计时”表示没达标；朱红线是目标。
- 学习成本单列；不能只因为第二轮便宜就说整个流程省钱。

## 5. 回退（1 分钟）——“回退只切换指针，历史都在”

「04 版本管理」：

1. 版本链：v0 → … → 最终快照，朱红“生效”标记。
2. 选 v0，填写原因“演示回退”，点击“设 v0 为生效版本”。指针历史新增一行。
3. 回到运行页，下拉框显示当前生效版本为 v0；如果时间允许再跑一次，可以看到“本次实际读取的经验（v0）”为空。
4. 演示结束后切回最终快照（同样操作，或执行 `uv run routeevo snapshots activate v6 --reason 演示结束恢复`）。

## 6. 日新方向：两轮现场演示（可替代第 2 节）

「00 总览」底部的“两轮现场演示”卡片：

1. 第一轮选一个 A 任务（推荐 A-02、A-04、A-06 这类 Qwen 通常 1 次请求完成的任务），第二轮选一个没参与学习的 B/C 任务，基础快照选 v0。
2. 点击“开始两轮演示”。程序依次：第一轮学习运行（读 v0）→ 自动发布新版本（父版本 v0）→ 第二轮在 v0 与新版本下各跑一次同一任务 → 生成三行说明。中间不需要任何人工操作，模型、提示词、预算、评测器都不变。
3. 每个阶段完成后卡片打勾，可以点进第一轮的决策账本和第二轮的对照页（含行为对照：同一任务两种快照各做了什么）。
4. 整体约 3—5 分钟，取决于模型是否需要升级；单次运行时长按实测展示，不承诺固定秒数。
5. 演示后到「04 版本管理」把生效版本切回最终快照。

## 7. 常见问题

| 问题 | 回答要点 |
| --- | --- |
| 经验是模型自己总结的吗？ | 不是。程序从结构化执行记录中提取事实；模型的解释另存为未验证假设，不额外调用模型做总结。 |
| 怎么防止模型作弊？ | 候选在禁网、只读的容器里运行，只拿到 stdin；参考输出和最终测试数据不进容器；7 个契约用例防止只对当前数据分布正确的程序。 |
| 加速是不是噪声？ | 交替测量 5 轮，只有全部候选样本快于全部基线样本才算改善；同一个程序测出 1.05× 也不会被记成改善。 |
| B 和 C 有什么区别？ | B 用于开发期对照，可以据此调整；C 在配置冻结后只跑一轮，结果不用于调优。 |
| 费用怎么算？ | 每次调用记录服务方返回的用量，按带版本的官方价表估算；没有用量就记“未知”，不写 0；本地 Qwen 无 API 费用，机器成本单列为未核算。 |
