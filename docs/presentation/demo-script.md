# QuotaCrux 现场演示脚本

目标时长 8—10 分钟。顺序按 PRD 第 11 节：研究问题、预算和基线 → 一条真实的证据—假设—实验—修正链 → 最佳方案、独立结果和资源用量记录 → 系统本身的评估。历史实验标明运行时间，现场演示另开新运行。

## 0. 开场前（提前 15 分钟）

```sh
open -a OrbStack                                 # Docker
ollama ps                                        # 确认 qwen3.8:27b-mlx 已加载；没有就先跑一次 probe 预热
cd backend
uv run quotacrux probe small                      # Qwen 预热，期望 10—20 s 内返回 propose_candidate
uv run quotacrux probe large                      # GPT 连通性，约 20 s、约 $0.01
uv run quotacrux snapshots list                   # 确认生效版本是 v19（* 标记；分组聚合两轮学习的最终快照）
uv run quotacrux serve                            # 浏览器打开 http://127.0.0.1:8000
```

- 浏览器全屏，缩放 110%—125%，投影上数字要清楚。
- 打开「运行」，确认“开始运行”按钮可用，顶栏没有“运行中”提示。

## 1. 研究问题、预算和基线（1 分钟）

打开「运行」，选 A-01 的第一版学习运行（`#run/run-20261113T161733-7c5a`），展开“研究任务 · 运行开始前固定”：

- 研究问题：在输出完全正确的前提下，能否让这段分组聚合程序在该输入规模和特点上至少快 1.10×？
- 基线：初始程序（csv + 两个 dict + sorted），开发数据中位耗时 0.679 s。
- 允许修改、工具、验证方法、预算（6 次请求、4 个候选、300 秒）都在开始前固定，模型改不了；最终测试数据不可见。

## 2. 一条真实的研究链（1.5 分钟）——“反馈改变了下一步”

同一页往下看“假设与实验”和“决策账本”：

1. Qwen 的假设：按字节解析、bytes 作 key 能省掉 str 转换，预期 ≥ 1.10×。实测 **0.90×，判定被反驳**。
2. Qwen 据此修正：“c1 慢是因为 bytes key”，改用 str key——但输出格式错误，**未能检验**。
3. 连续两次未达标，程序按固定规则**升级到 GPT**（账本写明触发条件）。
4. GPT 读到具体反馈，提出批量分行 + 单字典：**1.45×，得到支持**，达标后停止。
5. 判定由程序根据评测给出，不是模型自评；失败和被反驳的实验都留在记录里。

展开“模型用量明细（按角色与模型）”，核对各生成模型与路由角色的请求数、Token、费用和累计请求耗时。

原生任务的模型策略补充材料见[一小时双机对照](../research/onehour-20261114/README.md)及[展示图](../research/onehour-20261114/quality-requests.png)。可用 desktop 自适应组说明另一条实际研究链：5 个 dev 用例上的分数从 44120 经六个模型候选升至 46855，按 dev 冻结 c6 后，在 15 个 final 用例上得到 140262。讲解时将过程记录、同机策略对照和费用未知项一起展示。

若展示 Decisions 的作用，明确它只负责有限动作选择，Qwen/Sol 仍负责分析和代码生成，模型升级沿用规则。补充实验的 14 次动作决策中位耗时 1.34 秒，路由累计费用估算约 $0.015；这是低开销接入的证据。该批全部选择生成候选，整轮研究仍大体耗满预算，尚不能用这组数据宣称整轮加速。

## 3. 对系统本身做研究（1.5 分钟）——第一版的发现与第二版的修改

打开「更多 → 经验阶段」（`#hist`），先看下方的 C 批（第一版，只有文字经验）：

- 有经验后请求 3 → 1、费用下降、达标率不变，但**最终加速比中位数 1.41× → 1.29×**。
- 诊断：经验里已经有完整的好程序，Qwen 却要花一次请求把它重抄一遍（A-04 的“新”候选与 A-01 的 GPT 程序逐字相同）；而且一达标就停，用不上 GPT 找到的更快方案。
- 修改：经验保存完整程序；新任务首次请求前，由程序复验条件最接近的 ≤ 3 个已验证程序。评测运行复验达标即交付；学习运行把目标提高到超过已知最佳 5%，模型只做“超越”。
- 公平性：修改后重新学习、重新对照；C 已经用来诊断，所以在写第二版代码之前新封存了 D 批（提交 `d542906`），只跑一次。

## 4. 第二版的学习与验收（1.5 分钟）

1. 「运行」打开一次第二版学习运行（推荐 A-06 第 1 轮）：前三步是“程序 · 复用已验证程序”，没有模型参与；随后“提高本次目标”，模型以最佳复用程序为父候选提出超越方案，判定按当时目标给出。
2. 「更多 → 经验阶段」（`#hist`）看学习阶段：A 批两轮，各任务最终加速比逐轮提高（数字见 `docs/archive/memory-learning-results.md` 2.1）。
3. 看 D 批（封存留出）与 B 批（开发对照）的条带：达标率、最终加速比中位数、模型请求、GPT 费用、循环时长。点“逐任务详情”进入「经验对照」，也可从「更多 → 经验对照」（`#cmp`）进入，看逐任务点图。
4. 说明成本和失败情况：学习阶段本身花钱更多（学习运行用 GPT 去超越已知最佳），学习成本单列；经验覆盖不到的输入规模和特点（分组数多），复验不达标，照常交给模型研究。

## 5. 第三版：遇到全新问题——分流器与在线记忆（2 分钟）

1. 「更多 → 经验阶段」（`#hist`）：S 任务流条带下方是分流表（四条路线、各自的条件和留下什么）。强调判断由程序按经验覆盖情况做出，不由模型自评；完整的边界条件见 `docs/archive/legacy-runtime-rules.md`。
2. S 任务流条带：同一串 12 个任务（3 个任务族交替出现）× 3 次重放，带记忆 vs 不带记忆的达标、大模型请求、费用、总耗时。点“逐任务详情”进入「经验对照」：累计大模型费用的折线——带记忆一侧只在任务族首次出现时上升，之后是平的；逐任务表里每个符号是一次重放的路线（↺ 复用、★ 全新任务族 → 大模型）。
3. 分流器对照（实验结果 2.3 节）：同样的新任务族，先用本地 Qwen 与直接用 GPT 都全部达标；直接用 GPT 更快（循环时长中位数 49 → 33 秒）、第一个答案更好（2.11× → 2.18×），每个新任务多约 $0.012。
4. 说明使用限制：复用达标即交付，不为单个任务追求最优；其他任务族的经验不算数；无法程序验证的任务不做。

## 6. 现场新跑：一个全新问题，然后一个相似问题（约 1.5 分钟）

「运行」→“发起运行”：任务选 **T-L1**（访问日志统计），模式“**在线 · 交付并记住**”，快照选 **v19**（只有分组聚合的经验），点击“开始运行”。

预期：账本第 2 步是“程序 · 分流：快照中没有任务族 logstats 的任何经验，按全新问题直接交给大模型”，GPT 一次提出候选，约 30 秒达标（几倍加速），费用约 $0.02；运行结束时发布新版本，运行页“本次实际读取的经验”区域显示新发布的快照。

接着再新建：任务选 **T-L2**（条件不同的访问日志），模式“在线”，快照选刚发布的版本。预期：程序复验刚学到的程序，**模型请求 0、费用 $0**，约 20 秒交付。

任务流对照见前述结果。演示结束后在「更多 → 版本」（`#ver`）把生效版本切回 v19。

如果网络不可用：任务选 D-01、模式“评测”、快照 v19，复验直接交付，同样是 0 次模型请求。

## 7. 交付与回退（30 秒）

- 运行页“导出研究记录（Markdown）”；完整交付包见 `docs/research/`：研究记录、`best.py`、全部候选、原始模型调用、`reproduce.sh`。
- 「更多 → 版本」（`#ver`）：选 v0，填写原因，设为生效版本，指针历史新增一行；之后的运行读取 v0，历史全部保留。演示后切回 v19。

## 8. 常见问题

| 问题 | 回答要点 |
| --- | --- |
| 怎样使用旧程序？ | 复用的是经验快照里版本化、可回退、可追溯来源的已验证程序；每次都在新任务的数据上重新评测，未达标就不用。v0 没有程序可复用，两边配置相同，只换快照。 |
| 这是研究还是在轮流试预设选项？ | 没有预设候选清单。复用的程序来自以前的实验；模型候选由模型根据实测反馈写出，账本里能看到“c1 慢是因为……”这类直接引用反馈的修正，学习运行还要超越已知最佳。 |
| 经验是模型自己总结的吗？ | 不是。程序从结构化执行记录中提取事实和程序；模型的解释另存为未验证假设，不额外调用模型做总结。 |
| 候选程序能访问哪些数据？ | 候选在禁网、只读的容器里运行，只拿到 stdin；参考输出和最终测试数据不进容器；7 个规则检查用例防止只对当前数据分布正确的程序。 |
| 加速是不是噪声？ | 交替测量 5 轮，只有全部候选样本快于全部基线样本才算改善；同一个程序测出 1.05× 也不会被记成改善。 |
| B、C、D、S 有什么区别？ | B 是开发对照，可以据此调整；C 是第一版配置冻结后的留出，结果用于诊断；D 在第二版实现前封存，第二版定型后只跑一次；S 是第三版运行前封存的任务流，混合 3 个任务族，配置在 T 上检查后只跑一次。 |
| 全新问题为什么不先试免费的本地模型？ | 分流器对照（实验结果 2.3 节）：同样的新任务族，两种做法都全部达标；直接用 GPT 时循环时长中位数 49 → 33 秒、最终加速比中位数 2.11× → 2.18×、没有失败候选，先用 Qwen 有 2 个候选失败、2 次升级。代价是每个新任务多约 $0.012。第一个答案会成为之后同类任务复用的起点，所以这笔钱花在第一次。 |
| 遇到完全不同类型的问题（比如问答）呢？ | 目前支持能用程序自动验证结果的任务。新任务族只要提供契约、初始程序、生成器、参考实现和检查器，就能接入。 |
| 费用怎么算？ | 每次调用记录服务方返回的用量，按带版本的官方价表估算；没有用量就记“未知”，不写 0；本地 Qwen 无 API 费用，机器成本单列为未核算。 |
