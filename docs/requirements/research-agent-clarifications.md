## 1. 赛题描述

> Research Agent系统设计: 构建一个面向研究场景的Research Agent System，在给定数据、工具和资源预算下，自主完成“规划—收集证据—提出假设—实验或分析—验证—修正”的研究闭环。
>
> 系统应使用本地模型/轻量模型承担持续执行与迭代工作，并根据任务难度、执行反馈和剩余预算，自主决定何时调用云端大模型完成复杂规划、关键判断或失败诊断，最终交付可追溯、可复现、可持续提升的研究成果。

题目给出的可选场景和指标：

> 可以自主选择机器学习，大模型算子提速，软件性能加速等场景做Agent能力的评估。评估指标包含云端模型使用成本，任务的完成度/加速比，任务的完成时间等。

## 2. 企业方补充原文

### comment1 模型数量与成本

> 这里描述的是实际工业场景的需求, 具体而言, 整个 research agent 系统中可能有多个 agent 分担不同的工作, 每个 agent 背后的任务复杂程度可能不同, 因此可以灵活选择从而降低 token 成本. 在比赛中, 如果只有一个 llm 可用, 那么所有的 agent 都依赖那个 llm, 不用考虑在本地跑 llm. 但你依然可以考虑一些 "token成本" 层面的问题.

### comment2 本地轻量模型

> 因此, 你可以忽略 "本地轻量模型" 这件事.

### comment3 研究任务与系统重点

> 具体的研究任务可以自由选择, 考虑到本地的算力, 可以优先选择一些相对轻量的任务. 例如, 假设我有一批表格数据, 我需要对它做分类, 传统做法是由一个研究员先分析场景和需求, 然后看数据, 做数据清洗和特种工程, 选择模型, 尝试训练模型并进行调参, 做评估和验证, 最后给出解决方案. 再例如, 我想基于一些已有的结果做一些数学或其他理论相关的研究, 传统做法是由研究员自己产生 idea, 然后进行尝试和验证. 本题希望通过一个 agent 系统代替研究员来完成这些工作, 所以本题的重点不在于 "这个研究任务是什么", 而在于你 "如何使用 agent 来做研究".

### comment4 系统本身的评估

> 既然我们的目标是做这个系统, 那当然也需要一个针对这个系统本身的评估, 例如, 它花了多少 token? 能在多长时间里给具体研究任务的性能指标带来多少提升? agent 是否可以自我迭代并改进? ...

## 3. 对本项目的具体影响

| 补充口径 | 本项目采用的实现与验收方式 |
| --- | --- |
| 单 LLM 也可参赛，本地轻量模型可忽略 | 模型数量和新增本地部署不作为赛题门槛；团队已主动选择接入现有 Qwen 服务与云端 GPT |
| 多个 agent 是可能的工业组织方式 | 首版采用一个研究执行循环，用阶段与结构化记录表达规划、假设、实验和修正 |
| 研究任务可自由选择，优先轻量场景 | 首版使用已正确的 Python 分组聚合程序做性能优化，任务是评估研究系统的载体 |
| 重点在如何使用 Agent 做研究 | 必须展示事前假设、工具证据、真实实验，以及反馈如何改变下一步；成果包括可运行方案和复现入口 |
| 评估系统的成本、时间、改进能力 | 分别报告产物性能和 Agent 效率；全量记录失败尝试与模型用量，使用独立测试和冻结经验对照 |

研究闭环是当前主线。经验版本、失败经验、回退和 A/B/C 对照继续用于验证可持续改进；日新的专属两轮会话与三行说明保留在历史方案中。

## 4. 团队已确认的选择

| 项目 | 确认内容 |
| --- | --- |
| 参赛方向 | 已选择 Research Agent，确认日期为 2026-11-14 |
| 小模型 | 使用自部署 Qwen，准确 model ID、服务协议与地址由部署方提供 |
| 大模型 | OpenAI GPT-6.1 Sol，推理强度 xhigh |
| 调用预算 | 现阶段先不限制金额；保留用量账本和防止无限运行的次数、超时约束 |
| 凭据 | 用户私下提供给开发 agent，不写入仓库文档 |
| 开发与演示环境 | 可以使用 Docker，正式对照固定同一台机器和 Docker 环境 |

上述是团队明确回复的内容。任务包数量、测量次数、初始升级规则等属于[开工决策](../archive/implementation-decisions.md)中的首版实施口径，可在开发数据上校准，正式对照前冻结。专用决策模型仍为后置实验项。
