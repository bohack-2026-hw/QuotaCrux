# 单个研究任务内持续优化：评测方案

日期：2026-11-14；状态：协议调整，尚未执行新协议的正式对照。实现核查基线：`cd41e5a`，分支 `feat/effibench-x-adapter`。

本方案落实 [Research Agent 补充说明](research-agent-clarifications.md)中的研究闭环与系统效率要求，并替代主线 PRD 中把跨任务经验对照作为主要系统评测的安排。当前代码、既有任务锁及[历史实验结果](results.md)保留。

## 1. 要验证的主张

一个研究任务对应一个独立 episode：Agent 在固定问题、工具和资源预算内，依据已有实验的反馈选择、修正后续方案，最终交付经独立评价的成果。

主要验证三件事：

1. 最终产物相对初始基线改善多少，是否满足正确性或可行性约束。
2. 在同样预算下，利用前序反馈是否优于相互独立地尝试多个方案。
3. 随着本次研究继续进行，最佳成果、耗时、Token 和费用如何变化；哪些实测反馈改变了后续行动。

同一候选多次计时用于降低测量波动；同一问题开展多轮实验用于研究；从头重复整个 episode 用于观察 Agent 波动。这三种重复分别记录。跨题目、跨 session 的经验迁移属于扩展实验，不作为主线成立的前提。

## 2. 对照设计

首轮采用两个实验组，均从空的跨任务经验快照 `v0` 开始，不读取其他 episode 的产物，也不发布供后续评测使用的经验。

| 实验组 | 本次研究中可用的信息 | 交付选择 |
| --- | --- | --- |
| 反馈迭代 | 原始任务、初始方案、开发工具，以及本 episode 的代码、测量结果、失败信息和研究记录 | 开发评价最好的可行候选 |
| 独立尝试 | 每次候选尝试都重新从相同原始任务、初始方案和公共证据开始；候选间不传递代码、得分、失败信息或总结 | 外部评测器在所有尝试中按同一开发规则选择最佳可行候选 |

独立尝试组可以使用同样的静态分析工具，但生成一个候选并取得开发反馈后即结束该次尝试，下一次重新初始化。外部选择器保留得分不等于向生成器反馈。API 错误、非法输出和失败候选都消耗各自预算，不赠送额外尝试。

首轮两组固定使用同一生成模型和参数，先采用已接通的 Qwen 配置，关闭升级与额外决策模型，避免同时改变反馈利用和模型能力。模型的准确 ID、服务方与采样参数以该批冻结 manifest 为准。该对照回答反馈利用的作用；现有 Qwen/GPT 及决策模型调度的完整系统表现另列，不能把单模型对照结论直接写成两层路由的收益。

每组固定相同的任务版本、初始程序、开发/最终数据、依赖与硬件、工具权限、候选筛选规则和预算上限。两组提示词只在事前登记的信息传递规则上不同。按题目和重复编号交替顺序串行运行，完整报告所有 episode。

## 3. 预算与停止

以下是 RouteEvo 的试验预算，不是候选 benchmark 的官方标准预算。当前 `300s / 6 请求 / 4 候选` 仍是已实现默认值。

| 阶段 | 题目与重复 | 每个 episode 的拟定上限 | 用途 |
| --- | --- | --- | --- |
| 接入预检 | 1 题，固定程序，无模型调用 | 单独记录安装、编译、基线和裁判耗时 | 检查环境、正确/非法输出判定和单次测量代价 |
| 开发 pilot | 1 题 × 2 组 × 1 次 | 15 分钟、20 次模型请求、10 个候选 | 校准上下文、实验吞吐与费用；研究时长上限合计 30 分钟 |
| 首轮正式对照 | 2 道事前选定的题 × 2 组 × 3 次 | 30 分钟、40 次模型请求、20 个候选 | 12 个 episode，研究时长上限合计 6 小时 |

任何一项上限先耗尽就结束；实际停止原因必须报告。若 pilot 显示请求或候选额度过早截断研究，只能在正式批次冻结前调整并登记。60 分钟预算可作为另一个事前登记的实验档位；不能看过最终成绩后只延长不利运行。3 次重复只用于展示波动，不足以单独支持强统计结论。

- 开始计时后，规划、证据工具、候选生成、编译、开发评价、失败修复和模型等待均计入研究墙钟；环境安装与公共预检单列。
- 最终候选在研究预算内冻结。独立最终评价单列耗时，另报告包含它的端到端耗时与总成本。它不返回研究循环。
- 达到 `1.10×` 只作为性能任务的里程碑，正式持续优化模式不据此自动停止；正常结束条件为 Agent 主动完成、资源耗尽或明确错误。允许无改进和提前完成，不人为拖长运行。
- 在 5、15、30 分钟保存当时已完成验证的最佳候选及累计资源。跨过检查点才完成的候选不倒填；提前结束后曲线保持已取得结果并标注终止。
- 调用/工具开始前依据剩余预算约束超时，在途请求无法取消产生的超时余量与费用另记；预算后才完成的实验不进入预算内成绩。
- 每次调用记录输入/输出/推理或缓存用量（服务支持时）、请求用途、模型和状态。继续沿用现有可选 Token 额度；多模型实验须统一覆盖生成、升级和决策调用。金额暂不设硬上限，人民币与美元分别报告，未知费用不能记为零。

## 4. 数据隔离与计分

每题的公开开发数据可反复用于研究，私有最终数据由独立裁判持有。最终评价前冻结产物哈希、依赖、配置与预算账本；不能按最终结果换候选。pilot 已看过的私有数据不得继续宣称为正式配置开发期间完全封存的留出集；需要另选题或预先隔离新的最终用例。

首选安排是 pilot 只使用公开开发评价，不开启私有最终评价，以保留同题的最终用例用于正式对照。

主线不要求 A 批学习后再跑 B/C。多个题目是多个独立研究 episode。跨任务迁移扩展才使用原有 A 学习、B 开发、C/D 留出及冻结经验快照。

| 指标 | 报告口径 |
| --- | --- |
| 正确性 / 可行性 | 每个候选开发验证结果、最终候选私有通过数及总数；非法输出、超时、编译失败与基础设施错误分列 |
| 产物效果 | 性能题报告初始程序/最佳候选的同环境加速比；优化题报告原生目标分数及其方向，不把质量分数称为加速比 |
| 过程收益 | 开发最佳有效结果随墙钟、累计 Token、累计费用的曲线；另报首个可行结果和首次达到预登记目标的时间，未达到就明确标记 |
| 最终效果 | 独立最终结果、相对初始方案的变化、两组逐题配对差值；所有重复均展示，不只挑最佳一次 |
| 研究成本 | 完整模型请求、Token、原币种费用、编译/工具/裁判耗时、研究墙钟与端到端墙钟；共享准备成本单列 |
| 行为证据 | 引用前次开发结果、事前假设、实际修改和后续结果，说明一次反馈如何影响选择；引用链不能只靠事后总结补写 |

开发曲线用于描述搜索过程，隐藏最终分数用于判断泛化。连续型得分在不同题目间量纲不同，首轮逐题报告，不自行平均原始分数。性能测量继续保存原始重复值；采用上游函数计时或 GPU 计时的任务不能沿用进程启动计时冒充内核性能。

## 5. Benchmark 安排

详细来源、规模和限制见[长时研究与优化 benchmark 调研](long-horizon-benchmarks.md)。

1. **主线优先 ALE-Bench。** 原生目标是同一问题内持续提高解的质量；CPU 即可执行。候选为 Lite 中的 `ahc026`（搬箱子）和 `ahc024`（拓扑地图），按任务性质预选，尚未观察 RouteEvo 效果。pilot 和正式留出安排须在读取私有结果前冻结。
2. **AlgoTune 作为性能优化备选。** 可选择 `convolve_1d` 与 `pagerank`，复用运行时间目标，但需数值库、容差校验和函数计时。当前标准库镜像不能直接运行。
3. **KernelBench 作为可用 GPU 的备选。** 用户提供 `ssh desktop` 的 RTX 2080 Ti；先验证工具链与小规模 Level 1 算子，固定该卡实测自己的基线，再考虑融合任务。
4. 现有 groupagg 和 EffiBench-X 保留为功能回归、快速端到端检查及历史性能结果。MLE-bench、RE-Bench 记录为研究任务参考，首轮不扩大到完整 ML 训练环境。

## 6. 开跑前必须补齐的实现

本次只调整评测方案与需求文档，下表均为新正式对照的前置事项，不表示已实现。

| 当前代码事实 | 所需改动 |
| --- | --- |
| `agent/runner.py` 在候选达标或复用达标时 `goal_reached` 停止 | 为本协议提供预算内持续优化行为，保留现有短演示行为；阈值作为里程碑 |
| `compare.py` 只对照不同经验快照，并要求配置指纹相同 | 支持预登记的“反馈迭代 / 独立尝试”差异，检查其余冻结条件；不能绕过配置一致性校验 |
| 当前候选选择和报告以正确性、speedup 为核心 | 接 ALE-Bench 时仅增加确实需要的原生分数、方向、可行性、最佳候选规则及展示，不重建通用框架 |
| 标准库 Python 沙箱与 stdin/stdout 计时 | 按所选 benchmark 接入原生裁判/镜像；编译与测量分别记账，最终数据继续隔离 |
| 预算主要在步骤边界检查 | 实现上述时间截断和完整费用记账，保存检查点的真实完成时间 |
| 各 worktree 可有独立运行目录和进程锁 | 与本地和远端 agent 协调同一测量窗口，CPU/GPU 测量不争抢同一资源 |

首轮预检通过后再冻结正式实验配置。环境可运行、适配器正确、Agent 有收益是三种不同结果，分别交付。

## 7. 与并行开发的衔接

本方案不修改 `Runner`、模型路由、决策 API 或服务部署。正式实验前统一记录选定的 RouteEvo 提交、适配器版本、上游数据版本、模型配置和运行环境；不能将不同 agent 分支上的结果拼成同一次对照。

截至本次文档核查：`main=f8fbb3e`、`feat/shared-core=1bf9d49`、本分支基线 `cd41e5a`。两层路由在其他 agent 分支继续推进，其独立报告不代替本协议的反馈利用对照。协作信息统一更新到 [issue #1](https://github.com/bohack-2026-hw/RouteEvo/issues/1)。
